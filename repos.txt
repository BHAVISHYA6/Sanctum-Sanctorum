B. REQUIRED BUT NEEDS IMPROVEMENT

These are not failing acceptance requirements. They are architectural or production-hardening improvements identified by inspecting the actual design.

1. Database-level numeric checks

Book price_cents and stock, OrderItem quantity, and order monetary fields are validated in application schemas, but the database models do not add CheckConstraint rules. Direct SQL or another writer could insert negative values or invalid totals.

2. Database-level status and tier constraints

Member tier and order status are stored as strings. Python enums and service logic validate normal API paths, but PostgreSQL does not enforce the allowed values through database CHECK constraints or native enum types.

3. Delete behavior

The Order.items relationship has cascade="all, delete-orphan", which is appropriate for dependent order items. Member orders and loans do not define delete cascades, and foreign keys do not specify ondelete behavior. There are currently no delete endpoints, so this is not an active API failure, but the deletion policy should be made explicit before adding deletion operations.

4. Table initialization versus migrations

The application runs Base.metadata.create_all(engine) during startup. This works for a fresh database and passed the PostgreSQL verification, but create_all() is not a schema migration system. The assignment explicitly does not require Alembic at this stage, so this is a production improvement rather than missing assignment work.

5. Seed initialization concurrency

seed_if_empty() checks whether the database has data and then inserts seed rows. Multiple application instances starting simultaneously could race. A one-time deployment seed step or stronger coordination would be more robust for a scaled deployment.

6. Environment-file loading behavior

app/db.py reads the process environment with os.getenv(). It does not automatically parse the local .env file. This is acceptable for deployment providers, which inject environment variables, and for the controlled verification process that loaded .env explicitly. Local developers must either export SANCTUM_DATABASE_URL or use a tool that loads .env.

7. Connection and concurrency hardening

The PostgreSQL integration is verified, but production settings such as pool_pre_ping, pool sizing, connection lifetime, and deployment-specific connection limits should be reviewed for the selected host. Concurrent last-copy order protection is optional under ASSIGNMENT.md and is not counted as missing required work.

D. SCHEMA/MODEL REVIEW

Book

Purpose:

Stores the catalog and the current inventory state.

Fields:

- id: integer primary key.
- title: String(200), required through SQLAlchemy 2.x Mapped[str] inference and Pydantic validation.
- author: String(200), required.
- isbn: String(13), unique and indexed.
- price_cents: integer monetary value.
- stock: integer inventory count.
- restricted: boolean access flag.

Assessment:

This is the correct entity for current catalog price and stock. ISBN uniqueness is correctly enforced at the database level. Monetary values use integer cents as required. The model would be stronger with database-level nonnegative checks for price and stock.

Member

Purpose:

Stores members who can purchase and borrow books.

Fields:

- id: integer primary key.
- name: String(100), required.
- email: String(320), unique and indexed.
- tier: String(20), required in the ORM type inference.
- created_at: DateTime, required.

Relationships:

- orders: one-to-many to Order, ordered by Order.id.
- loans: one-to-many to Loan, ordered by Loan.id.

Assessment:

The entity correctly owns member identity and tier. Email uniqueness is enforced after schema normalization. Tier is stored as a string rather than a database enum/check constraint, so direct database writes are not protected from invalid tier values. No deletion cascade is specified.

Order

Purpose:

Represents a purchase transaction and its lifecycle.

Fields:

- id: integer primary key.
- member_id: foreign key to members.id and indexed.
- status: string lifecycle value.
- subtotal_cents: integer.
- discount_percent: integer.
- discount_cents: integer.
- total_cents: integer.
- created_at: DateTime.

Relationships:

- member: many-to-one Member.
- items: one-to-many OrderItem with order_by=OrderItem.id and delete-orphan cascade.

Assessment:

The aggregate structure is appropriate. Order owns its items, and the cascade matches the dependent nature of order items. The status should ideally have a database constraint or enum. Monetary and discount invariants are enforced in service code, not at the database layer. The member foreign key is correct.

OrderItem

Purpose:

Represents one submitted book line in an order.

Fields:

- id: integer primary key.
- order_id: foreign key to orders.id and indexed.
- book_id: foreign key to books.id and indexed.
- quantity: integer.
- unit_price_cents: integer snapshot.

Relationships:

- order: many-to-one Order.
- book: many-to-one Book.

Computed property:

- line_total_cents = unit_price_cents * quantity.

Assessment:

This is correctly modeled as a separate table rather than an embedded JSON array. unit_price_cents correctly preserves the historical order price after a book price changes. The API response intentionally excludes the internal OrderItem id. A database CHECK constraint for quantity >= 1 and nonnegative unit price would strengthen integrity. The current domain intentionally uses the current Book title for reports instead of snapshotting the title.

Loan

Purpose:

Represents one borrowing transaction for one book and member.

Fields:

- id: integer primary key.
- member_id: foreign key to members.id and indexed.
- book_id: foreign key to books.id and indexed.
- borrowed_at: required DateTime.
- due_at: required DateTime.
- returned_at: nullable DateTime.
- late_fee_cents: integer defaulting to zero.

Relationships:

- member: many-to-one Member.
- book: many-to-one Book.

Assessment:

The model correctly represents borrowing and return state without storing a redundant status column. Status is derived from returned_at and the current clock, so it cannot become stale. The late fee is persisted because it is a historical charge. Stock belongs to Book because it represents current inventory shared by sales and loans. A database check for nonnegative late fees and explicit nullable/default declarations would strengthen the model. Concurrent last-copy protection is not implemented, but it is explicitly optional in the assignment.

Primary keys and foreign keys

All domain tables have integer primary keys. Relationships use foreign keys for Member-to-Order, Order-to-OrderItem, OrderItem-to-Book, Member-to-Loan, and Loan-to-Book. Foreign-key columns are indexed where appropriate.

Unique constraints

Book.isbn and Member.email are unique and indexed. There is no separate uniqueness constraint on active loans or order item book IDs, because the services and request schemas enforce those API rules and the order model allows one line per book by contract.

Nullable columns

The important nullable domain field is Loan.returned_at. Other Mapped non-Optional fields are inferred as non-nullable by SQLAlchemy's 2.x typed declarative mapping. Explicit nullable=False and database checks could improve readability and direct-database protection.

Enums and statuses

Python enums are used for MemberTier and OrderStatus, but model columns store strings. Loan status is intentionally computed rather than stored. PostgreSQL will behave correctly through the normal application path, but database-level status constraints are absent.

PostgreSQL behavior

The schema was created successfully against the real Supabase PostgreSQL database. SQLAlchemy 2.x Mapped declarations, integer money values, foreign keys, indexes, and relationships are PostgreSQL-compatible. The main remaining production concern is schema evolution because create_all() is not migrations.

E. API SCHEMA REVIEW

Book schemas

- BookCreate separates creation input from BookOut.
- Title and author use stripped bounded string constraints.
- ISBN is normalized and checksum-validated through a field validator.
- BookUpdate contains only patchable fields and uses Optional fields with exclude_unset semantics in the service.
- ISBN and unknown fields are ignored for PATCH because they are not declared and Pydantic defaults to ignoring extra fields.
- BookOut uses from_attributes=True for ORM serialization.
- BookPage wraps items with total, limit, and offset.

Member schemas

- MemberCreate separates input from MemberOut.
- MemberTier validates the allowed tier values.
- Email normalization occurs before validation and persistence.
- MemberStats exposes only the specified aggregate fields.
- MemberOut exposes the public member fields and timestamp.

Order schemas

- OrderItemIn contains only book_id and quantity.
- quantity >= 1 is validated by Pydantic.
- OrderCreate requires at least one item and rejects duplicate book IDs with a model validator.
- OrderItemOut exposes the public item contract and omits the internal database row ID.
- line_total_cents is supplied through the ORM property.
- OrderOut contains nested items and all required monetary/status fields.

Loan schemas

- LoanCreate contains only member_id and book_id.
- LoanOut contains persisted timestamps and late fee plus the computed status returned by the service.
- Loan status is not stored in the database, preventing stale status values.

Report schemas

- TopBook contains exactly book_id, title, and copies_sold.

Overall schema assessment

The Pydantic layer correctly separates request, update, and response contracts. It keeps internal ORM identifiers out of nested order responses and keeps computed loan status in the service serialization path. Database-level validation is less strict than API-level validation, which is acceptable for the assignment but worth strengthening for systems with other database writers.
